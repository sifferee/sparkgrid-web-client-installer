# AGENTS.md — общая память между Claude / Qwen / Hermes

Этот файл — не документация проекта, а мост между инструментами. У каждого
ИИ, с которым ты работаешь, контекст обнуляется между сессиями и не виден
другим инструментам. Единственное, что видно всем — то, что лежит в
репозитории. Этот файл — часть репозитория специально для того, чтобы
следующая сессия (любым инструментом) не начинала с нуля.

ПРАВИЛО: открывай (или проси инструмент открыть) этот файл в начале КАЖДОЙ
сессии. Перед тем как закончить сессию — обнови секцию "Последнее изменение"
и, если нужно, "Известные баги".

## Роли

- **Hermes** — единственный инструмент, который пишет и коммитит код
  напрямую в репозиторий. Если Claude или Qwen предлагают патч — он идёт
  через Hermes, а не применяется руками параллельно.
- **Claude** — диагностика сложных багов, ревью, архитектурные решения,
  готовые промпты/патчи для Hermes.
- **Qwen** — [впиши, для чего используешь конкретно]

## Золотые правила

1. Только один инструмент пишет в репозиторий в один момент времени. Не
   гонять два агента параллельно на одних и тех же файлах.
2. Перед началом сессии — `git log -5 --oneline`, посмотреть что изменилось
   с прошлого раза и каким инструментом (см. секцию ниже).
3. Коммит после каждого осмысленного изменения, с сообщением "что и почему",
   не "fix"/"wip"/"update".
4. Любой инструмент, закончив сессию с реальными изменениями в коде,
   обновляет секцию "Последнее изменение" ниже — дата, что сделано, каким
   инструментом, номер коммита.

- **[ПЛАН, не начато] Пройтись по веб-дашборду отдельно.** За всю
  сегодняшнюю сессию не открывали и не проверяли веб-интерфейс вообще
  (только бэкенд/бот) — а у Александра там есть UI с нишами (скриншот
  "Scale niches" — All Scale/Unassigned/tast/test dlya Hernes, счётчики
  accounts/queued/ready), возможно и другие разделы. Нужно: пройтись по
  дашборду, посмотреть что там реально показывается, найти что не
  работает или выглядит не так как должно. Пока не начато — ждёт когда
  Александр будет готов заняться этим отдельно.

- **[ПЛАН, не начато] Скриншоты + текст ошибки в отдельный раздел бота.**
  Обсуждено с Александром 11.08. Данные для этого уже есть — дампы
  (снапшоты) при сбоях уже пишутся на диск, текст ошибки уже есть в БД
  по каждому job'у, просто сейчас никуда автоматически не уходит.
  Технически: либо push (бот сам присылает при появлении новой ошибки),
  либо pull (команда типа /errors по запросу), можно оба. "Отдельный
  раздел" — либо отдельный топик в супергруппе (если топики включены),
  либо отдельная команда/кнопка в меню бота.
  ВАЖНО: Александр явно сказал — это ТЕСТОВАЯ версия на период пока он
  тестирует софт, после тестирования планирует ОТКЛЮЧИТЬ. Значит при
  реализации: (а) делать легко выключаемым одним флагом/командой, не
  вплетать намертво в обычный поток уведомлений; (б) не удивляться и не
  спорить, когда попросят выключить — это заранее оговорено, не
  внезапная отмена.

- **Notifications "Not now" — клик формально ok=False, но логин всё равно
  доходит до logged_in.** Всплыло в тесте на 7 аккаунтах (11.08):
  madeleineycz3, hayleydnqk, eleanorwk9 — 3 из 3 случаев. Дальше НЕ

  "removed post" (искать в дампах точную метку, или живой скриншот).
- **"Try again" при заливке рилса — всё ещё не поймано.** 3 захода на
  диагностику, 0 совпадений в дампах за весь август (121
  success/36 manual_required/33 failed проверены). Код там уже
  продуманный (retry x3, гибкий текстовый поиск) — баг не на
  поверхности. Единственный рабочий путь дальше — живой скриншот от
  Александра в момент когда он это увидит (сработало для "removed
  post" именно так).
- **Красные кружки в уведомлениях о логине — источник не найден.**
  Проверено: НЕ в patches/ (единственный 🔴 в коде — про
  протухшие/забаненные аккаунты, другой контекст). Значит часть базового
  приложения вне git. Блокирует батчинг логин-уведомлений (см. раздел
  аналитики ниже, принцип 5).
- **CLI-путь логина (`--task auto_login` напрямую, в обход
  connection_scheduler.py) — не известно используется ли в реальной
  работе.** Спрошено у Hermes дважды, ответа не было ни разу. У CLI-пути
  нет вообще никакой защиты (ни ретраев, ни удаления) — если он реально
  используется для живых аккаунтов, это отдельная задача.
